# 디자인 역량과 평가 하네스 강화 계획

기준일: 2026-11-14. 상태: **일부 반영, 나머지 제안**. 1.16.3 작업본에서 `visual-design`의 콘텐츠 구조·이미지 아트 디렉션·매체별 검토 지침과 공개 개발 사례를 추가했고, 1.16.4 작업본에서 디자인 작업 흐름과 원본·렌더·검토 기록의 오프라인 해시 정합성 검사를 추가했다. 이 문서 자체가 스킬 설치, HTML/PPTX 변환기 구현 또는 실제 시각 품질 검증을 뜻하지는 않는다. 작업 범위는 `skill-myway`이며 다른 저장소는 읽기 전용 참고 대상으로 둔다. 명시적으로 허용되지 않은 경로 쓰기와 사용자 승인 없는 computer use는 하지 않는다.

## 1. 목표와 현재 증거

웹·이미지·문서·발표자료에서 정보의 의미가 바로 읽히도록 콘텐츠 구조, 시각적 위계, 매체별 표현과 실제 출력 검증을 한 흐름으로 연결한다. 편집성과 접근성, 자료의 권리·출처를 함께 평가한다. 스킬 이름이나 템플릿 수보다 사용자가 이해하고 활용할 수 있는 결과를 우선한다.

현재 `visual-design`은 공통 원칙, 콘텐츠 구조·이미지·매체별 지침과 선택형 평가표를 제공하고, `office-docs`는 브랜드와 형식별 절차를 갖고 있다. `document-authoring`은 공통 근거와 문서 간 의미 대조를 다룬다. 새로운 중복 스킬을 만들지 않고 기존 스킬의 책임과 연결을 확장했다. 참고: `plugins/myway/skills/visual-design/SKILL.md`, `plugins/myway/skills/office-docs/SKILL.md`, `plugins/myway/skills/document-authoring/references/cross-format.md`.

기존 10개 경계 시뮬레이션에서는 문자열 통과가 의미 정확성을 보장하지 못했고, 참고 파일이 이전 manifest의 해시에 들어가지 않았다. 작업본은 스킬 트리 해시, 엄격한 케이스 입력, 자동 판정과 최종 판정 분리를 추가했다. 이는 파일 단위 회귀 증거이며 실제 모델의 시각 품질 통과는 아니다. `SIMULATION-2026-11-14.md`, `SIMULATION-FIX-2026-11-14.md` 참조.

이 계획을 작성한 뒤 다시 실행한 Windows 전체 테스트는 210건 중 오류 1·실패 1이었다. 정상 출력 사례의 10초 timeout과 자손 시작 표식 미확인이 관찰됐다. 프로세스 제어 테스트만 다시 실행했을 때도 5건 중 오류 2·실패 1로 timeout과 시작 표식 미확인이 반복됐다. 원인은 아직 확인하지 못했으며 이전 실행 통과를 이번 실행의 통과로 대체하지 않는다. 프로세스 제어의 원인과 종료 보장 범위를 별도 조사할 필요가 있다.

Claude·Codex의 실제 평가 6회는 OCR·문장 의미 3개 사례에 한정됐다. 스킬 본문 로드는 관측됐지만 참고 문서 로드는 플랫폼·사례마다 차이가 있었다. 공개 사례, 단회 실행, 다른 모델·권한 조건, 자기 점검이므로 디자인 능력 향상이나 모델 우열을 증명하지 않는다. 실측 기록은 `eval-results/actual-1794631837518/REPORT.md`에 보관돼 있다.

`docs/RENDER-GATE.md`의 일부 설명은 현재 코드와 어긋난다. 문서는 기존 파일 구조 검사가 없다고 기술하지만, `scripts/check_office.py`에는 `inspect_office_file`·`inspect_office_artifacts`가 있고 `scripts/run_eval.py`에서 선택적으로 호출한다. 이것이 렌더·편집성·접근성 검증을 이미 제공한다는 뜻은 아니다. 구현 전에 실제 연결과 지원 범위를 테스트로 재확인하고 해당 문서의 상태를 정정한다.

## 2. 제안 구조: 공통 디자인 판단 + 매체별 제작

1. **과제와 콘텐츠:** 청중, 전달할 결론, 데이터 근거, 사용 맥락, 형식, 편집성, 제약과 검토 방법을 확정한다. 페이지별 핵심 메시지와 그 메시지를 지지하는 요소를 연결한다.
2. **표현 선택:** 비교·변화·과정·구조·증거·행동 유도 중 내용에 맞는 표현을 고른다. 같은 카드나 텍스트 박스를 모든 장에 반복하지 않는다. 수치의 단위, 축과 관계는 원천과 대조한다.
3. **아트 디렉션:** 정보 위계, 글꼴·한글 줄바꿈, 그리드·간격, 색과 대비, 이미지의 역할을 정한다. 기존 브랜드와 사용자가 지정한 양식이 우선이다.
4. **매체별 구현:** HTML/CSS, 그림·SVG, 편집 가능한 PPTX, 문서 구조가 있는 DOCX, 배포용 PDF 각각의 특성에 맞는 생성기를 사용한다. 한 형식의 성공을 다른 형식의 성공으로 간주하지 않는다.
5. **실제 결과 검수:** 구조·의미·권리와 실제 렌더를 각각 검사하고, 발견한 결함의 위치·증거·수정 상태를 기록한다. 화면을 보지 못했다면 시각 품질은 미검증이다.

## 4. HTML 미리보기와 PPTX의 관계

사용자가 최종 확정 전 HTML을 선호하는 발표자료에는 **같은 슬라이드 모델에서 HTML과 PPTX를 생성**하는 방식을 후보로 둔다. 이는 기존 PPTX 렌더 검토를 대체하는 승인 절차가 아니다.

- 공통 모델에 슬라이드 크기, 텍스트·의미·좌표·색·글꼴·계층·도형·차트와 자산 참조를 명시한다. 형식에서 지원하지 않는 기능은 누락하지 말고 오류 또는 미지원으로 보고한다.
- PPTX를 다시 읽어 모델과 텍스트·도형·순서·좌표·스타일을 대조한다. 허용 오차는 사전에 정하고 수치 대조에 포함할 속성과 제외 사항을 명시한다.
- 같은 값이라도 글꼴 대체와 엔진 차이로 줄바꿈·높이·시각 결과는 달라질 수 있다. PowerPoint의 자동 맞춤은 글꼴 크기나 줄 간격을 바꿀 수 있으므로 설정과 결과를 확인한다. [Microsoft Open XML 자동 맞춤 설명](https://learn.microsoft.com/en-us/dotnet/api/documentformat.openxml.drawing.normalautofit). 좌표 대조만으로 시각 동일성을 보증하지 않는다.
- 각 렌더러의 버전과 글꼴을 기록하고 HTML 미리보기와 PPTX에서 뽑은 렌더를 나란히 비교한다. 시각 차이 탐지는 후보 발견에 사용하고 의미 있는 차이·한글 잘림·편집성은 별도 확인한다. 검증에 실패하거나 지원하지 않는 표현은 PPTX 인도 단계에서 중단한다.
- 일부 이미지 기반 고정 렌더는 외관 차이를 줄일 수 있으나 텍스트·차트 편집성과 접근성을 제한한다. 사용자의 편집성 요구를 만족하는 경우에만 선택지로 제시한다.
- DOCX·반응형 HTML에는 내용 흐름이 필요한 경우가 많으므로 동일 좌표 모델을 강제하지 않는다. 공통의 것은 근거와 디자인 의도이며 형식별 실측 결과는 별개다.

## 6. 제작·평가 실행 순서

1. **현재 상태와 기준선:** 기존 스킬 라우팅·게이트 문서·코드 연결을 조사하고 실제 재현 결과를 기록한다. 평가용 가상 주제와 필요한 형식을 정한다.
2. **대표 작품:** 같은 검증된 주제를 사용해 한 장의 비교형 화면, 발표 슬라이드 3장(대비·관계·의사결정), 문서 2쪽과 인포그래픽 1개를 만든다. 사용자 요청이 있으면 형식을 조정한다. 모두 같은 원천 수치와 출처를 사용한다.
3. **기준본 평가:** 실제 결과물에서 핵심 결론을 찾을 수 있는지, 위계·정렬·문장 밀도·의미 손상·잘림을 사전 기준으로 기록한다. 독자가 없다면 독자 이해도는 미검증이다.
4. **한 번에 하나의 가설:** 예를 들어 `나열형 비교를 축과 근거가 있는 비교로 바꾼다`만 변경한다. 각 슬라이드의 정보 구조가 실제로 달라졌는지 전후 이미지를 대조한다.
5. **기능별 검증:** 형식별 구조·렌더·편집성·접근성을 따로 검사하고, 결함이 확인된 부분을 고친 뒤 영향 범위를 재검증한다. 참고 문서 로드·파일 이력·품질 판정도 각각 반례를 실행한다.
6. **동일 조건 비교:** 사용 가능한 경우 Claude·Codex에서 같은 작업·입력·모델별 설정과 예산을 고정해 각각 기준본/후보를 실행한다. 플랫폼 간 우열을 추정하지 않는다. 평가자는 정해진 기준으로 익명화된 결과를 비교하고 미실행·불완전 쌍을 남긴다.
7. **결정:** 필수 의미·권리·실제 출력 검증을 통과한 결과만 채택한다. 시각 완성도는 사람의 구체적 관찰과 실제 독자 반응으로 평가하고, 자동 점수·구조 검사만으로 승인하지 않는다.

대표 슬라이드는 같은 제목·박스를 반복하지 않는다. 예를 들어 **가상 데이터**에서 작업 소요가 100분에서 70분으로 바뀌었다면, 첫 장은 변화와 조건을 큰 수치·보조 설명으로 보여주고, 둘째 장은 변경 전후 과정과 검증 범위를 연결선으로 나타내며, 셋째 장은 도입 여부에 필요한 장점·제약·미확인 항목을 의사결정 표로 구성한다. `30분` 차이는 계산 예시이며 실제 측정이나 성능 주장이 아니다. 각 장의 제목과 도식이 전달하는 결론을 발표자가 한 문장으로 설명할 수 있는지 확인한다.

위험도가 높은 단계가 검증되지 않으면 이를 표시하고 의존하는 완료 주장을 보류한다. 반복 횟수·호출·시간·비용 한도는 실행 전에 과제별로 정한다. 사용자에게 HTML 승인을 받았어도 최종 PPTX는 별도 렌더와 파일 검증이 필요하다.

## 7. 라이선스와 운영 경계

- 외부 저장소의 기법을 참고할 때 구체적 코드·문구·템플릿·폰트·이미지·데이터를 그대로 가져오지 않는다. 실제 도입 시 고정 버전과 파일별 라이선스, 저작권·고지·변경 표시·모델 자산 조건을 확인하고 `LICENSES.md`에 기록한다.
- 새 로직이나 문장 작성은 권리 적합성을 자동 보증하지 않는다. 과거 권리관계와 법적 판단이 미확인인 자료는 이 계획으로 해결됐다고 표시하지 않는다.
- 모델·외부 렌더러에 보내는 자료와 사용자의 승인된 경로를 제한한다. 외부 도구 설치, 다른 프로젝트 수정, 전송·게시·배포와 computer use는 허용된 범위에서만 수행한다.
- 이 계획의 HTML·PPTX 공통 모델, 시각 차이 게이트, 독립 평가, 실제 산출물의 전 형식 검증은 **미구현 또는 미검증 제안**이다. 사용자가 보는 실제 화면·PPTX를 만들고 비교하기 전에는 시각 품질 향상을 주장하지 않는다.
