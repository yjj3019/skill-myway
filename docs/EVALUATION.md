# 스킬 평가

최고 성과를 비교·입증할 수 있는 조건과 남은 준비물은 `docs/MEASUREMENT-READINESS-2026-11-14.md`에 정리한다. 문서 준비는 실제 독립 평가나 최고 성과 달성을 뜻하지 않는다.

전체 11개 스킬의 공개 개발용 실측 입력, 쌍별 미실행 장부와 실행·개선 절차는 `docs/ALL-SKILL-MEASUREMENT-PLAN.md`를 따른다. 이 자료의 준비는 모델 호출이나 품질 향상 검증을 뜻하지 않는다.

스킬·지침 변경이 실제로 나아졌는지 판단하는 절차다. 모델 출력은 흔들리므로 한 번의 성공으로 품질을 주장하지 않는다.

공통 필수 게이트와 스킬·하네스별 평가 항목, 점수별 판정 기준은 `docs/QUALITY-RUBRIC.md`를 사용한다. 배포 요건은 `docs/QUALITY-BAR.md`가 정본이다.

## 의미·완료 근거 검토

`run_eval.py`의 `passed_auto_checks`와 종료 코드 0은 문자열·길이 등 **자동 검사만** 뜻한다. 자동 검사 PASS도 의미 품질은 `NOT VERIFIED`다. 목표와 실측의 관계가 바뀌거나, 단어만 있는 답변, 근거 없는 저장·렌더·테스트 완료 선언을 이 검사만으로 배제할 수 없다. 케이스에 맞는 세부 기준을 사전에 정하고 출력, 입력과 실행 추적·산출물을 보고 별도 검토한다. 출력에 없는 파일이나 화면을 본 것으로 간주하지 않는다.

공개 개발용 공통 기준은 `tests/eval_cases/review-rubric.json`이다. 이 기준은 의미 보존, 요청의 충실성, 완료 주장과 관측 근거를 별도로 판정한다. 케이스에 따라 목표 10·실제 8, 백업 조건, 가설과 확정 원인, 화면 부재, 저장·테스트 수행 여부 등 구체적인 판단 기준을 **실행 전** 별도 rubric에 명시한다. 공개 기준과 공개 사례는 최종 미노출 평가가 아니다.

`scripts/review_evaluation.py`는 출력과 기준의 SHA-256에 결부된 리뷰 기록의 누락·중복·불일치를 검사한다. 사용 예시는 다음과 같다. 결과와 리뷰에는 민감정보가 있을 수 있으므로 저장소 밖에서 보관한다.

```text
python scripts/review_evaluation.py --template OUTPUT.md RUBRIC.json REVIEW.json
# REVIEW.json의 reviewer, independent, 각 기준의 status, reason, evidence 작성
python scripts/review_evaluation.py OUTPUT.md RUBRIC.json REVIEW.json
```

각 기준은 `PASS`, `FAIL`, `NOT VERIFIED` 중 하나다. 필수 근거가 지정된 기준의 PASS에는 구체적인 근거 위치가 필요하다. `declared_result`는 입력된 판정을 요약한다. `verdict`는 FAIL이 하나라도 있으면 FAIL, 그 외에는 언제나 NOT VERIFIED다. 근거 문자열과 독립성 선언만으로 근거의 진위·검토자 독립성·판정의 정확성을 확인할 수 없기 때문이다. 리뷰 검사 명령의 종료 코드는 검증 완료를 나타내지 않도록 1이다. 동일 작성자의 점검은 `independent: false`로 기록한다. 이 도구는 실제 파일, 로그, 화면이나 테스트의 진위를 자동으로 판정하지 않으며 임의의 거짓 주장 전체를 기계적으로 탐지하지 않는다.

파일 근거의 존재와 무결성을 확인할 때는 각 `evidence` 배열에 `{"path": "relative/file.txt", "sha256": "..."}` 객체를 넣고 `python scripts/review_evaluation.py --evidence-root EVIDENCE_DIR OUTPUT.md RUBRIC.json REVIEW.json`을 실행한다. 해시는 파일의 실제 SHA-256 소문자 64자리다. 경로는 지정된 디렉터리의 상대 경로이며 경로 이탈·링크·존재하지 않는 파일·해시 불일치를 거부한다. 각 파일은 최대 1 MiB다. 검사된 파일이 있으면 `evidence_file_integrity: PASS`를 기록하지만 이는 해당 시점의 바이트 일치만 뜻한다. 파일 내용의 진실성·관련성·평가자의 독립성과 동시 변경 방지는 검증하지 않는다. 일반 문자열 근거는 이 선택적 파일 검사 없이만 사용한다.

평가자가 검토할 때는 (1) 목표·실측과 조건의 관계가 그대로인지, (2) 요청한 구조와 내용이 빠지지 않았는지, (3) 실행·파일·화면 관련 완료 주장이 있으면 해당 실행 로그와 산출물이 있는지 각각 확인한다. 근거가 없는 경우 `NOT VERIFIED`, 반례가 확인되면 `FAIL`이다. 자동 문자열 검사의 결과와 리뷰 결과를 합산하거나 같은 의미의 PASS로 보고하지 않는다.

추출 자료 공개 개발 사례의 사전 수동 판정 기준: `research-brief-extraction-loss-01`은 18의 단위·표 관계·페이지를 확정하지 않는지, `research-brief-search-negation-01`은 원문의 미지원과 검색 조각의 차이를 보존하는지, `document-authoring-ocr-table-01`은 12와 8의 행 관계·단위·페이지를 만들지 않는지 확인한다. 해당 위치에 실제로 접근했다는 허구의 주장도 실패다. 세 공개 사례와 자동 문자열 조건만으로 일반적 모델 품질을 입증하지 않는다.

## 격리 테스트 환경

일반 타깃 평가에서도 `artifact_policy`와 `expected_extensions`를 manifest에 보존한다. 파일 필수 케이스는 `--platform codex --cases FILE --inspect-artifacts`가 필요하며, 검사 설정이 없으면 모델 호출 전에 거부한다. 검사 모드에서 필수·금지 파일과 확장자를 확인한다. 파일 정책을 관측하지 않은 실행은 자동 통과로 집계하지 않는다. 파일이 조건부이고 보존·검사를 요청하지 않았다면 생성 금지 프롬프트를 사용한다. 프롬프트는 쓰기 차단 장치가 아니다.

시간 초과는 `runs[].status: timeout`과 케이스별 `timed_out`으로 집계한다. `completed + execution_failed + timed_out + not_run = repeats`다. 종료 코드가 0이어도 Codex 실패 이벤트가 관측되면 실행 실패다.

오프라인 고장 주입 절차는 `docs/WORKFLOW-SIMULATION-2026-11-14.md`를 따른다. 외부 경로 쓰기가 허용되지 않은 세션에서는 `TEMP`·`TMP`를 승인된 프로젝트 내부 임시 경로로 지정하고 기존 Python 환경을 사용한다. 아래 환경 생성 예시는 해당 경로 사용이 허용될 때만 적용한다.

저장소 밖 가상 환경을 만들고 `requirements-test.txt`를 설치한 Python으로 검증한다. 예를 들어 Windows PowerShell에서는 다음과 같다. `soffice`의 PATH와 버전은 별도 확인한다.

```powershell
python -m venv "$env:TEMP\skill-myway-test-env"
& "$env:TEMP\skill-myway-test-env\Scripts\python.exe" -m pip install -r requirements-test.txt
& "$env:TEMP\skill-myway-test-env\Scripts\python.exe" scripts/validate_repo.py
& "$env:TEMP\skill-myway-test-env\Scripts\python.exe" scripts/run_tests.py
& "$env:TEMP\skill-myway-test-env\Scripts\python.exe" -m unittest discover -s tests
```

고정된 직접 의존성 이외의 하위 의존성까지 완전 고정하거나 OS·네트워크 환경을 격리한 절차는 아니다. 환경과 실패·skip을 기록한다.

## 개선 실험 운영

1. **계획을 먼저 고정한다.** 변경 전 지침과 후보의 버전·내용 해시, 개선할 문제, 예상 효과와 반증 조건을 적는다. 입력 집합, 판정 기준, 반복 횟수, 호출·시간·비용 상한과 중단 조건도 실행 전에 정한다. 예: 특정 누락을 줄이되 하드 실패가 늘지 않아야 채택한다. 수치 상한은 과제와 가용 자원에 맞춰 정하며 임의의 보편 합격선으로 쓰지 않는다.
2. **동일 조건으로 대응시킨다.** 각 케이스와 반복 번호마다 기준선과 후보를 짝짓고, 같은 요청·모델 버전·설정·도구 접근·시간 제한으로 실행한다. 지침 외 차이는 적고 통제할 수 없으면 비교 한계를 표시한다. 순서 편향을 줄이도록 실행 순서를 교차하고, 사람 검토는 가능하면 출처와 순서를 가린다. 실행 순서와 배정 키는 별도 보관한다.
3. **결과를 빠짐없이 세고 비교한다.** 사전에 정한 전체 케이스×반복을 분모로 두고, 각 쪽의 실행 실패·시간 초과·빈 출력·판정 불가를 각각 기록한다. 양쪽 유효 출력이 있는 쌍과 그중 사람 판정까지 완료돼 방향 비교가 가능한 쌍을 별도로 센다. 판정 완료 쌍만 개선·악화·동일을 비교하며, 전체 예정 쌍과 각 단계에서 빠진 이유를 함께 보고한다. 미채점을 성공이나 실패로 임의 환산하지 않고, 한쪽만 실행된 쌍도 누락하지 않는다. 자동 검사 결과와 사람의 의미 판정은 별도다. 안전 등 하드 실패는 평균에 묻지 않고 개별 보고한다.
4. **실패도 다음 선택의 근거로 남긴다.** 시도마다 가설, 변경 내용, 실제 호출 수·경과 시간·비용(확인 불가 시 미확인), 예산 잔여, 결과와 실패 원인을 기록한다. 상한에 도달하거나 중단 조건이 발생하면 새 시도를 멈추고 미실행분을 밝힌다. 후보 채택·기각·판단 보류와 근거를 적고, 기준선보다 낫다는 증거가 부족하면 보류한다.

### 평가 오염 방지

- 개발 중 살펴보는 사례와 최종 확인용 사례를 분리한다. 최종 사례·정답·판정 메모는 지침 작성이나 반복 튜닝에 제공하지 않고, 요청과 판정 기준을 최종 실행 전에 고정한다. 이 저장소에 공개된 사례는 노출된 개발·회귀 사례이지 비공개 최종 평가가 아니다.
- 최종 결과를 보고 지침이나 기준을 수정했다면 그 사례는 개발용으로 전환하고, 별도로 준비한 미노출 사례로 다시 확인한다. 미노출 사례가 없으면 독립 확인은 **미검증**이다. 실제 데이터는 사용 권한과 민감정보를 확인하고 기록에는 최소한만 남긴다.
- 빈 임시 작업 디렉터리를 사용해 저장소의 지침·훅 혼입을 줄이되, 사용자·전역 설정, 캐시, 네트워크와 플랫폼별 자동 로드까지 격리된다고 가정하지 않는다. 접근 가능한 환경과 로드된 지침을 확인·기록하고 확인하지 못하면 한계로 남긴다. 스킬 트리 해시는 생성 시점의 파일 내용을 기록하며 실제 로드와 런타임 전체를 보장하지 않는다.

| 항목 | 기록할 내용 |

| 가설 / 사전 기준 | 개선 대상, 악화 허용 여부, 반증·중단 조건 |
| 범위 / 예산 | 사례 집합 구분, 예정 쌍·반복, 호출·시간·비용 상한과 실제 사용량 |
| 결과 | 예정 쌍, 양쪽 유효 쌍, 개선·악화·동일, 실행 실패·미채점 및 이유, 하드 실패 |
| 판단 / 다음 행동 | 사람 판정 근거, 한계, 채택·기각·보류, 실패한 시도와 후속 조치 |

## 기록

- 입력 요약, 사용한 모델·설정, 두 출력, 축별 점수, 하드 실패 여부.
- 판정자와 판정 시각, 애매한 지점.
- 결론은 "이 조건에서 이 차이"로 한정한다.

## 쌍별 판정 집계

### 디자인·문체 개선 평가 흐름

1. 변경 전에 목적, 대상 매체·독자, 사례, 실패 조건, 실행 예산과 수동 판정 기준을 기록한다. 평가에 쓰인 사례는 개발용으로 취급하고 독립 최종 평가는 별도로 준비한다.
2. 같은 입력·도구·화면 크기·데이터 조건에서 기준선과 후보를 각각 실행한다. 실행 환경과 변경된 조건, 시간 초과 및 미실행을 남긴다. 환경을 같게 만들 수 없으면 비교의 한계를 밝힌다.
3. 문체는 원문에 있는 조건·부정·수치·인용·불확실성 보존과 독자의 이해를 살핀다. 한 표현의 출현, 탐지기 점수나 자동 문자열 검사만으로 자연스러움을 판정하지 않는다.
4. 디자인은 실제 결과의 확인 범위와 시각적 위계·가독성·잘림을 살핀다. 화면 크기와 사용 상태를 기록하고 키보드·접근성·기능은 별도 증거로 평가한다. 보지 않은 화면은 미검증이다.
5. 가능한 경우 출처를 가린 독립 판정을 사용하고, 그렇지 않으면 독립 판정 부재를 기록한다. `compare_evaluations.py`에는 확정된 판정과 미완료 상태를 함께 입력하며 작은 표본으로 일반적 품질 향상을 주장하지 않는다.

`python scripts/compare_evaluations.py RECORD.json`은 이미 기록된 쌍별 판정을 오프라인으로 집계한다. 모델 호출, 사람의 평가, 원본 기록 인증과 후보 채택은 수행하지 않는다. 입력의 `judgment_source`는 `human` 또는 `automatic` 하나이며 서로 섞지 않는다. `planned`에 예정된 쌍을 먼저 나열하고 `trials`에 각 쌍을 정확히 한 번 기록한다. 누락·중복·예정 외 항목은 거부한다. 각 쌍의 `case`와 양의 `repeat` 조합은 유일해야 하고, 두 조건의 값은 `PASS`, `FAIL`, `UNJUDGED`, `TIMEOUT`, `ERROR`, `NOT_RUN` 중 하나다. 예정된 쌍은 결과가 없어도 `NOT_RUN`으로 입력한다.

```json
{
  "schema_version": 2,
  "judgment_source": "human",
  "context": {
    "baseline": {"cases": "set-a", "rubric": "r1", "scorer": "s1", "environment": "e1", "model": "m1", "execution_budget": "b1", "tool_configuration": "t1", "prompt": "p1"},
    "candidate": {"cases": "set-a", "rubric": "r1", "scorer": "s1", "environment": "e1", "model": "m1", "execution_budget": "b1", "tool_configuration": "t1", "prompt": "p1"}
  },
  "planned": [{"case": "sample-a", "repeat": 1}, {"case": "sample-b", "repeat": 1}],
  "trials": [
    {"case": "sample-a", "repeat": 1, "baseline": "FAIL", "candidate": "PASS"},
    {"case": "sample-b", "repeat": 1, "baseline": "TIMEOUT", "candidate": "NOT_RUN"}
  ]
}
```

출력은 예정·양쪽 판정 완료·미완료 쌍과 양쪽 상태별 건수만 제공한다. 동일한 조건을 선언해도 실제 환경이나 사전 계획의 일치를 증명하지 않는다. 조건 값이 없으면 `null`로 표시하며, 누락이나 차이가 있으면 맥락을 `UNVERIFIED`로 남긴다. 입력에는 민감정보를 넣지 않는다. 출력은 사례 식별자와 조건 값을 포함하지 않지만, 입력 파일 자체는 별도로 보호한다.

버전 2는 모델·실행 예산·도구 구성·공통 과제 프롬프트도 비교한다. 각 값은 실제 버전이나 설정을 구별할 수 있는 비민감 식별자로 기록한다. 의도한 스킬 변경은 비교 대상이므로 공통 과제 프롬프트와 구별한다. 기존 버전 1은 계속 집계하지만 네 추가 조건이 없어 맥락은 항상 `UNVERIFIED`다. `DECLARED_MATCH`도 선언값의 일치일 뿐 실행 증거나 판정의 진위를 확인하지 않는다.

## 한계

- 자동 점수는 형식만 본다. 의미 품질은 사람이 판정한다.
- 모델이 바뀌면 결과가 달라진다. 오래된 결과를 현재 성능으로 쓰지 않는다.
- 표본이 적으면 우연과 차이를 구분할 수 없다.

## 결과 지표의 분모

비교 전에 작업·반복·판정자·예산·실패 기준을 고정하고 다음 수치를 함께 기록한다. 분모가 0이거나 필요한 관측치가 없으면 비율은 미확인으로 둔다.

| 지표 | 분자 / 분모 | 별도로 남길 것 |
| --- | --- | --- |
| 검증 성공률 | 독립적으로 검증 완료된 작업 / 실제 시도한 작업 | 전체 예정 작업, 미실행·실패·미판정 수. 자체 확인만 있으면 독립 검증으로 세지 않는다. |
| 주장 근거 일치율 | 대조 결과가 출처와 일치한 주장 / 실제 판정한 검증 대상 주장 | 전체 추출 주장, 출처 부재·판정 대기와 오류를 따로 기록한다. 미판정 주장을 빼고 전체 정확도로 부르지 않는다. |
| 독자 이해도 | 사전에 정한 질문에 정답인 응답 / 실제 채점한 응답 | 대상 독자군, 질문·채점 기준, 참여하지 않았거나 미채점인 인원을 밝힌다. |
| 문서 무결성 | 확인 결과 통과한 필수 검증 항목 / 실제 판정한 필수 항목 | 전체 예정 항목, 미실행·미확인과 실패를 병기한다. 형식·렌더·수식·편집·접근성의 서로 다른 검사를 하나로 대체하지 않는다. |
| 거짓 완료율 | 완료 선언 후 검증 실패로 판정된 작업 / 완료를 선언한 작업 | 미검증 선언이 남으면 비율은 현재 확인된 하한으로만 표시하고 미검증 건수를 병기한다. 최종 거짓 완료율은 모든 선언을 판정하기 전까지 미확인이다. |
| 완료당 비용 | 전체 시도의 확인된 비용 / 검증 완료된 작업 | 실패·재시도 비용도 포함한다. 비용 일부가 빠지거나 분모가 0이면 전체 비용·비율은 미확인이다. CLI 보고액과 청구액을 구분한다. |
| 복구 성공률 | 장애 주입 후 정해진 안전 조건을 만족한 복구 / 실제 장애 주입 시도 | 미실행·중단·검증 불가, 장애 유형과 상태를 기록한다. |
| 회귀율 | 이전 통과 후 이번에 실패한 대응 사례 / 이전 통과 후 다시 판정된 대응 사례 | 재실행하지 않았거나 미판정인 사례는 분모 밖에 두되 예정 건수와 함께 표시한다. |

동일 사례·환경·예산의 기준선과 후보를 짝지어 비교한다. 표본과 미완료 사유를 병기하고 작은 표본으로 일반적인 향상을 확정하지 않는다. 원문 사실성·시각 점수·독자 이해도는 각각 별도 판정 근거가 필요하다. 이 표는 지표를 자동 측정하는 실행기가 아니다.

## 블라인드 패킷

`scripts/blind_review.py`로 A/B 순서를 섞은 검토 패킷과 비공개 키를 만든다.

```sh
python3 scripts/blind_review.py --cases cases.json \
  --candidate-1 a.json --candidate-2 b.json \
  --packet packet.json --key key.json
```

- 케이스 형식: `id`, `source`, `required_claims`, `protected_spans`.
- 후보 형식: 케이스 id마다 비어 있지 않은 문장.
- 키에는 seed·배정·해시가 들어간다. 검토자에게 주지 않는다.
- 같은 seed로 재현할 수 있고, 기존 파일은 덮어쓰지 않는다.
- 도구는 모델 호출·채점·의미 동등성 판정을 하지 않는다. 판정은 사람이 한다.
- 패킷에서도 후보 출처를 알 수 없지만, 문장 자체에 출처·민감정보가 남을 수 있으므로 두 파일과 키를 보호한다.

## 독립 시각 리뷰

- 검토자에게 요청 목적·대상 사용자·필수 시각 조건과 현재 산출물의 식별자·버전을 제공한다. 제작 과정의 평가나 기대 결론은 제공하지 않는다.
- 현재 버전에서 생성한 전체 화면·페이지의 이미지 또는 렌더링과 원본 산출물을 가능한 범위에서 전달한다. 캡처 범위, 크기·해상도, 뷰어·렌더링 환경과 확인하지 못한 부분을 함께 밝힌다. 이미지에서 확인한 위치와 관찰을 근거로 쓰고, 시각 자료만으로 동작·정확성·접근성 전체를 보증하지 않는다.
- 자료가 없거나 열리지 않거나, 최신 버전과의 일치 또는 필요한 화면을 확인할 수 없으면 해당 범위는 **평가 불가능**으로 기록한다. 추측으로 점수를 채우지 않고 필요한 자료를 요청한다.
- 검토자는 제작자와 독립적으로 먼저 관찰과 개선점을 기록한다. 비교할 때는 식별 정보를 가리고 표시 순서를 섞되, 표현 자체에서 출처가 드러날 가능성을 한계로 남긴다.

## 실행 평가 (2단계)

1. **가상 테스트** — `python3 scripts/simulate_eval.py`
   - `tests/eval_cases/cases.json`의 케이스 스키마·id 중복·스킬 커버리지·민감 패턴을 검사한다.
   - 케이스별 요청과 스킬 트리의 파일별 해시 및 목록을 담은 manifest 버전 2를 만든다. `__pycache__`는 제외하고 링크·정규 파일이 아닌 경로는 거부한다. 본문 해시 `skill_sha256`은 호환을 위해 유지한다. 모델은 호출하지 않는다.
2. **실제 테스트** — `python3 scripts/run_eval.py --platform claude [--max-calls N] [--max-seconds N]`
   - 각 케이스에 스킬 지침을 적용해 모델을 실행하고 출력을 저장한다.
   - 필수 요소·금지 패턴·최대 길이를 자동 검사한다. `eval-results/summary.json`에 기록한다. Codex/Grok에서 Office 산출물 검사도 요청하면 `--inspect-artifacts`를 사용한다. 파일 구조·압축 경로·매크로 흔적·외부 관계를 확인하고 XLSX 계산 캐시 상태는 별도 표시한다. Claude 플러그인은 평가 작업 폴더 밖에서 로드되므로 이 옵션과 함께 사용할 수 없다.
   - 빈 출력은 자동 검사에서 실패하며, 실행 오류·시간 초과는 검사를 수행하지 않고 `checks: null`로 남긴다. 자동 검사는 형식과 필수 요소만 본다. 문장 품질·사실 정확성은 사람이 판정한다. 회귀 사례별 수동 기준은 `tests/eval_cases/visual-review-rubric.md`를 참고한다.
   - 일반 평가에서 긍정적인 내용 조건(`required` 또는 `ends_with`)이 없으면 비어 있지 않은 출력의 자동 판정은 `NOT VERIFIED`로 두고 통과율도 보류한다. 실행 실패나 다른 형식 검사의 실패는 실패로 기록한다. 자동 선택의 파일 정책 검사는 별개이며, 모든 실행의 의미 품질은 사람 판정 전 `NOT VERIFIED`다. 문자열이 들어 있어도 요구한 판단을 올바르게 했다는 뜻은 아니다.
   - Claude·Codex 원본 JSONL이 있으면 별도의 `.trace.jsonl`과 SHA-256을 기록한다. 시간 초과 시 회수 가능한 부분 출력과 작업 폴더의 산출물을 보존하고 실패 상태로 둔다. 이 파일에는 모델 출력·경로·설치된 플러그인 정보·민감 정보가 포함될 수 있으므로 결과 폴더를 보호하고 공개 전에 검토한다. 이벤트가 없거나 부분적으로만 기록되면 스킬 로드는 미확인이다.
   - Claude 지정 평가에서 `Skill` 도구의 해당 스킬 호출과 성공 결과, 현재 스킬 본문과 일치하는 전달 내용이 모두 관측될 때만 로드로 기록한다. Codex·Grok 지정 평가는 임시 폴더의 스킬 파일을 먼저 읽도록 요청한다. Codex는 성공한 파일 읽기의 출력(`aggregated_output` 포함)이 현재 스킬 본문 전체와 일치할 때만 로드로 기록한다. 로드 요청과 실제 로드 증거는 구분한다.
   - 비대화형 모델 프로세스에는 닫힌 표준입력을 전달한다. 시간 초과 시 완성된 메시지가 부분 JSONL에 있으면 결과 파일에 보존하되 그 실행을 성공으로 바꾸지 않는다.
   - Claude·Codex가 이벤트에 제공한 토큰 수와 CLI 보고 비용은 각 실행의 `usage`에 기록한다. 제공하지 않은 값은 `null`이다. 캐시 토큰과 입력 토큰의 포함 관계는 제공자에 따라 다르므로 임의로 합산하지 않는다. CLI 보고 금액은 추정치일 수 있으며 실제 청구액이나 절감액이 아니다. Grok의 사용량은 현재 수집하지 않는다.
   - Grok 평가기는 자체 생성한 임시 폴더의 스킬을 탐색하도록 `--trust`를 사용한다. 이는 평가 폴더 신뢰 설정이지 OS·네트워크 샌드박스가 아니다. 임의의 외부 작업 폴더에 이 옵션을 자동 적용하지 않는다.
   - 기존 결과 파일을 덮어쓰지 않으므로 실행마다 별도 출력 디렉터리를 지정한다. 저장 도중 오류가 나면 일부 파일이 남을 수 있다. 특수하거나 긴 사례 ID는 해시 파일명으로 저장한다. 트리 해시는 읽는 동안의 동시 변경을 방지하지 않으며 모델 버전·환경·실제 로드를 보장하지 않는다.
   - 사례 스키마 2는 선택적 `ends_with`로 공백을 제외한 응답 끝을 검사한다. 표의 행별 수치·의미·사실성은 자동 검사하지 않으므로 수동 판정한다. 구 실행기는 스키마 2를 거부한다.
   - Claude가 오류 종료하거나 결과 이벤트에 오류가 표시되고 확인된 영문 한도 메시지를 출력하면 남은 호출을 중단하고 `stop_reason`, `attempted`, `completed`, `execution_failed`, `not_run`을 기록한다. 미실행이 있고 자동 검사 실패가 없다면 케이스 `passed`와 `auto_check_pass_rate`는 `null`이다. 이 감지는 관찰된 문구에 한정되며 다른 형식·공급자나 결과 이벤트에 오류가 표시되지 않는 한도는 인식하지 못할 수 있다. 별도 병렬 실행 프로세스를 중단하지 않는다.
   - 요약의 `schema_version`은 4다. 이전 `pass_rate`는 자동 검사 전용인 `auto_check_pass_rate`로 바뀌었다. `auto_checks_passed`는 자동 검사 상태이며 최종 `passed`는 확인된 자동 실패에서만 `false`, 그 외에는 `null`이다. 자동 검사가 모두 통과해도 `overall_status`와 의미 품질은 `NOT VERIFIED`다. 종료 코드 0은 자동 검사만 통과한 상태다. 기존 소비자는 스키마 변경을 처리해야 한다.
   - 현재 실행기는 기준선·후보의 자동 대응과 블라인드 판정을 제공하지 않는다. 모든 실제 평가에는 `--max-calls` 또는 `--max-seconds` 중 하나 이상이 필요하며 둘 다 지정할 수 있다. 먼저 도달한 상한으로 남은 케이스를 미실행으로 기록한다. 둘이 동시에 충족되면 호출 상한을 우선 기록한다.
   - 시간 상한은 다음 호출의 시작 여부와 모델 CLI에 전달하는 timeout을 제한한다. 작업 폴더 준비가 끝난 뒤에도 잔여 시간을 확인해 소진됐으면 호출하지 않는다. 프로세스 생성·산출물 회수·정리, OS 스케줄링 및 자식 프로세스 종료까지 포함한 엄격한 전체 벽시계 기한은 보장하지 않는다. 비용 상한이나 네트워크·OS 격리도 강제하지 않는다. Codex `workspace-write`는 OS·VM 격리의 증거가 아니다.
   - `process_timeout_seconds`는 프로세스에 전달한 제한값, `preparation_seconds`는 작업 폴더 준비 시간, `process_seconds`는 프로세스 호출에서 복귀하기까지 측정 시간이다. `seconds`에는 준비·호출·일부 결과 처리가 포함되며 정리 작업은 포함되지 않는다. OS의 프로세스 생성·종료 지연으로 측정 시간은 제한값을 넘을 수 있다.
   - 가상 사례에서만 선택적으로 `forbid_unprovided_advisories: true`를 지정하면 요청에 없던 실제 연도 형식의 CVE/RHSA가 답변에 새로 나오면 자동 검사에서 실패한다. 요청에 포함된 식별자와 예약된 2099년 예시는 허용한다. 실제 보안 조사의 정확성이나 다른 형태의 허구 식별자를 판정하지 않는다.
   - `run_eval.py`의 `requires_followup: true` 사례는 첫 응답의 자동 검사 결과만 기록하므로 전체 사례를 통과시키지 않는다. 후속 대화를 실행하려면 아래의 `dialogue_eval.py`를 사용한다. 첫 응답에 특정 단어가 없다는 이유만으로 미래 행동의 실패를 추정하지 않는다.

### 후속 대화 자동 검사

`dialogue_eval.py`는 별도의 평가 도구다. `run_eval.py`가 첫 턴을 실행한 뒤 자동으로 호출하지 않는다. 사전 정의된 첫 요청과 후속 요청을 같은 Claude 또는 Codex 세션에서 각각 실행하고 세션 ID 일치·스킬 로드 추적·요청별 자동 검사·작업 폴더에 남은 파일을 기록한다. Grok의 세션 재개는 지원하지 않는다. 다음은 공개 개발 사례이며 출력 디렉터리는 아직 존재하지 않아야 한다.

```text
python scripts/dialogue_eval.py --platform codex --case rhel-cve-audit-missing --out EVAL_DIR --max-calls 2 --max-seconds 300 --timeout 120
```

호출 수는 두 턴을 각각 센다. 예산 소진·첫 턴 오류·세션 ID 누락 또는 불일치·시간 초과·스킬 로드 미확인 시 전체 후속 결과는 `NOT VERIFIED`다. 확인된 자동 조건이나 파일 정책 위반은 `AUTO FAIL`이다. 설치된 스킬 트리도 시작 시점과 각 턴의 해시를 비교해 변경을 검출한다. 두 턴의 자동 조건을 만족해도 `AUTO PASS`는 문자열·로컬 파일 스냅샷에 한정되며 의미 정확성은 `NOT VERIFIED`로 남는다. 한 번도 보이지 않은 파일의 생성 후 삭제, 외부 경로 변경, 모델의 안전한 행동이나 참값을 보증하지 않는다. 각 턴의 출력·원본 추적, 예산, 요청 해시 및 요약은 지정한 디렉터리에 저장하므로 민감정보를 검토하고 보호한다. 사례는 `tests/eval_cases/dialogue_cases.json`에서 사전에 정한다.

### 프로세스 종료 범위

평가 프로세스는 `scripts/process_control.py`를 거친다. Windows에서는 평가기가 직접 소유한 상속 불가 Job 핸들을 `scripts/windows_job.py`가 관리한다. 기본 Python의 표준 라이브러리만 사용하는 게이트를 breakaway가 허용되지 않는 Job에 넣은 뒤 실제 명령을 시작한다. 게이트에는 `-I -S -B`를 적용하지만 요청한 프로그램의 실행 파일·가상환경은 유지한다. stdin은 DEVNULL만 지원한다. 시간 초과·루트 종료·평가기 종료 시 핸들을 닫아 Job 멤버를 종료한다. 루트 종료를 기다리는 스레드가 Job을 닫으므로 자손이 출력 파이프를 상속해도 정상 종료를 막지 않는다. Job 할당 실패 시 명령은 시작하지 않는다. WMI 등 Job 바깥에서 생성된 프로세스나 호스트 지연에 따른 엄격한 벽시계 상한은 보장하지 않는다. [Microsoft Job Objects 문서](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects)의 범위를 따른다.

POSIX에서는 새 세션의 프로세스 그룹을 시간 초과 시 종료한다. 별도 세션으로 이탈한 프로세스까지 보장하지 않으며, 현재 Windows 이외의 실제 동작은 별도 확인이 필요하다. 어떤 방식도 네트워크 격리나 OS 스케줄링을 포함한 엄격한 전체 벽시계 상한을 제공하지 않는다.
