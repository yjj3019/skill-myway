# 증거 수집기 설계 제안 (2026-11-27, 미구현)

상태: **제안이다. 구현하지 않았고 승인 전까지 코드를 쓰지 않는다.** 이 문서의 모든 항목은 설계이며 동작 검증이 없다(NOT VERIFIED).

## 1. 문제

`check_evidence_answer.py`는 답변의 증거 ID가 fixture의 허용 목록에 있는 문자열인지만 본다. 모델이 지어낸 ID도 허용 목록과 같으면 통과하므로, ID가 실제 실행 기록과 연결된다는 보장이 없다(`answer-contract.md` 한계 절). 증거 ID를 모델 밖에서 발급해야 한다.

## 2. 설계 원칙

1. 모델은 증거 ID를 만들지 않는다. 호스트가 남긴 실행 로그에서 수집기가 만든다.
2. 정답과 증거 조건은 사람이 미리 고정하고 모델에 보이지 않는다.
3. 도구 결과 원문은 저장소와 장부에 남기지 않는다. 해시, 길이, 종료 코드, 도구 이름, 명령 요약만 남긴다.
4. 기존 검사기의 호환을 유지한다. 장부가 없으면 현재 동작 그대로다.

## 3. 구성

| 단계 | 산출물 | 내용 |
|---|---|---|
| P1 | `build_evidence_ledger.py` | Claude `stream-json` 로그의 `tool_use`와 짝이 되는 `tool_result`를 읽어 항목마다 ID를 발급한다. ID는 `ev-` 뒤에 도구 호출 ID와 명령과 출력 해시를 합친 값의 SHA-256 앞 12자리다. 항목: ID, 도구, 명령 요약, 종료 코드(있으면), 출력 SHA-256, 출력 길이, 오류 여부 |
| P2 | 검사기 `--ledger` | 장부가 있으면 ① 답변의 모든 ID가 장부에 있어야 하고 ② fixture의 필요 증거가 ID 대신 조건(`tool`, `command_regex`, `exit_code`, 선택적 출력 정규식)이고 ③ VERIFIED·CONTRADICTED 주장은 조건을 만족하는 장부 항목을 가리켜야 한다 |
| P3 | 합성 로그 시험 | 실제 모델 호출 없이 합성 `stream-json`으로 발급, 위조 ID 거부, 조건 불일치, 중복 도구 호출, 깨진 로그, 큰 출력을 시험한다 |
| P4 | 실측 1회 | 실제 Claude 실행 로그 1건으로 장부 생성이 되는지 확인한다(모델 호출 2~3회, 승인 후) |

## 4. 막는 것과 못 막는 것

- 막는 것: 지어낸 ID, 다른 실행의 ID 재사용(도구 호출 ID가 ID에 섞인다), 장부에 없는 항목을 근거로 쓰기.
- 못 막는 것(명시한다): 모델이 조건을 겨우 만족하는 사소한 명령(`echo` 등)을 실행해 통과를 노리는 경우는 조건이 느슨하면 통과한다. 조건은 명령, 종료 코드, 출력 패턴을 함께 걸어야 하며 그래도 의미 품질은 보증하지 않는다. 호스트 로그 자체가 변조되는 경우도 범위 밖이다.

## 5. 범위와 비범위

- 범위: Claude Code `stream-json`만. 이 형식은 현재 활성화 점검이 이미 읽는다.
- 비범위: Codex·Grok 로그(형식을 실측하지 못했다), 외부 서비스 호출, 장부의 저장소 보관, 답변의 의미 채점, 스킬 `description` 변경.
- 활성화 점검의 "도구 결과를 읽지 않는다" 규칙과 충돌하지 않도록 수집기는 별도 스크립트로 두고, 결과 원문을 읽되 해시만 남긴다.

## 6. 수용 기준

- P3 합성 시험이 전부 통과하고 테스트 0건·skip 0건이다.
- 위조 ID, 조건 불일치, 장부 없는 ID가 각각 종료 코드 1과 고유 위반 코드로 거부된다.
- 장부 없이 실행하면 기존 17건 시험이 그대로 통과한다.
- `validate_repo.py` PASS, 단독 ZIP 패키징 성공, 원격 CI 3개 OS 통과.
- 외부 자료를 참고하지 않고 이 저장소 안에서 독립 설계·구현했으며 겹침 검사 0건을 기록한다.
