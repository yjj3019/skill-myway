# skill-myway 개선 검토

> 현재 저장소를 검토한 2026-11-08 기준 메모. 기준은 `b00875c` 및 저장소 버전 1.14.7이다. 아래 과거 관찰은 당시 상태로 한정하며 현재 기능의 요약으로 읽지 않는다. 이번 검토에서는 모델 평가, 렌더링 또는 외부 도구를 실행하지 않았다.

## 핵심 판단

가장 큰 가치는 새 스킬 수를 늘리는 것보다 다음 흐름을 작고 검증 가능하게 연결하는 데 있다.

1. 자연어 요청을 해당 스킬·도구로 라우팅한다.
2. 필요한 근거를 모아 요청된 산출물을 만든다.
3. 구조·수식·렌더 결과를 서로 다른 범위로 확인한다.
4. 결과와 확인하지 못한 내용을 함께 전달한다.

최신 README는 이미 9개 스킬을 안내하고, 제안서 전용 업무는 별도 ProposalSkills를 사용하도록 구분한다. 이 경계를 유지한다. 큰 Office/장문 문서는 간결한 구조 미리보기 뒤 승인받아 생성하는 preview-first 정책도 `office-docs`에 있다.

## 우선 개선 제안

### 1. Office 실산출물 평가 확대

실제 업무자료 대신 권리와 민감정보를 확인한 가상 사례부터 쓴다. DOCX/PPTX/XLSX를 생성·재열기·검사하고, 필요한 경우 전 페이지/슬라이드를 렌더링한다. 구조, 수식 계산, 시각 배치, 접근성, 편집 가능성은 각각 별도 검사로 기록한다. LibreOffice 렌더와 Microsoft Office 표시가 같다고 가정하지 않는다.

**기대 효과 가설:** 전달 뒤 수정 요청을 줄일 수 있다. 실제 전후 비교 전에는 효과로 보고하지 않는다.

### 2. 스킬 선택과 다단계 라우팅 평가

사용자가 스킬명을 지정하지 않는 공개 합성 요청을 기본으로 한다. 각 흐름에 정상 요청, 입력 부족, 스킬을 부르면 안 되는 부정 사례, 여러 스킬 조합을 포함한다. 실행기 자동 통과와 사람의 업무 품질 판정을 분리한다. 실제 스킬 load 이벤트가 제공되지 않으면 선택 여부를 미확인으로 둔다.

**기대 효과 가설:** 사용자가 스킬 이름을 몰라도 올바른 시작점을 얻을 수 있다. 모델·CLI·케이스가 바뀌므로 반복 paired trial이 필요하다.

### 3. 글쓰기 사실 보존과 한국어 품질 측정

사실·수치·날짜·버전·명령·인용 출처가 편집 전후 유지되는지 검사하고, 문체는 블라인드 사람 평가로 별도 확인한다. 금지어 수를 늘려 자연스러운 표현을 억제하지 않는다. 샘플이 적으면 일반화하지 않는다.

### 4. 외부 도구 도입의 공급망 검토

후보마다 저장소 라이선스, 개별 스킬/하위 디렉터리/의존성의 조건, 네트워크·텔레메트리, 설치 스크립트 실행, 실행 권한을 분리해 검토한다. 라이선스가 불명확하거나 문제가 발생할 가능성이 있으면 원문·코드·프롬프트·에셋은 가져오지 않는다. 기능 요구만 추출해 다른 구조와 로직으로 새로 구현한다. 출처 메모는 사용 허가가 아니다.

외부 스캐너나 토큰 최적화 도구는 설치 후보일 뿐이다. 이 문서에서는 각 후보의 현재 라이선스나 실제 데이터 전송을 확인하지 않았으며, 포함된 명령·프롬프트·통계도 복사하거나 사실로 전제하지 않는다. 실제 사용 전에 버전별로 재검토한다.

### 5. 브랜드 재사용과 호환성

브랜드 프로필을 고객별 저장소 데이터와 분리한다. 템플릿이 제공되면 먼저 보존 범위와 변경 의도를 확인하고, 가상 문서에서 렌더·폰트·대비를 시험한다. 폴백 값이 있다고 해서 설치 환경에서 폰트가 실제로 사용된다고 보지 않는다.

## 과거 스냅샷에서 확인한 점

아래는 사용자 제공 자료의 분석 기준인 `e95afc2`/1.11.0에 대한 역사적 설명이다. 현재 저장소 설명으로 사용하지 않는다.

- 당시 `check_office.py`는 재열기 중심이었고 렌더링·넘침을 검사하지 않았다.
- 당시 run_eval은 평가 대상 스킬을 프롬프트에 명시했으므로 자동 선택은 별도 평가가 필요했다.
- 당시 문서에서 paired trial의 자동화 공백과 실행 격리 우려가 기록돼 있었다.

그 뒤 평가기와 Office 검사가 바뀌었다. 지금 남은 범위는 위의 현재 상태 표와 `docs/VERIFICATION.md`를 기준으로 한다.

## 후보 도구 다루기

이전 초안에 언급된 token-optimization, context-engineering, RTK 등은 검토 후보이지 채택된 의존성이나 검증된 권고가 아니다. 토큰 효율은 HTML 형식 자체보다 큰 산출물을 확인 전에 전체 작성·생성하지 않는 단계 분리에서 기대한다. 도입 전에는 라이선스와 데이터 흐름을 확인하고, 동일 작업에서 토큰, 재시도, 시간, 결과 품질을 함께 측정한다. 측정이 제공되지 않으면 절감률은 미확인이다.

## 이 문서의 한계

- 현재 평가·검증 상태는 1.14.7 및 `docs/VERIFICATION.md`에 기록된 범위에서만 기술했다.
- 이번 검토에서 테스트, 모델 실행, Office 렌더링, 네트워크 요청을 새로 수행하지 않았다.
- 외부 후보 도구의 최신 구현·라이선스·텔레메트리를 확인하지 않았다. 이름과 URL은 탐색 출발점일 뿐 도입 권고가 아니다.
- 제안한 효율·품질 효과는 사전 가설이다. paired trial과 사람 판정 전에는 개선 실적으로 보고하지 않는다.
