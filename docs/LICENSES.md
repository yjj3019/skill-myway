# 라이선스·출처 검토

기준일 2026-11-01. 이 저장소의 라이선스는 Apache-2.0이다. 통합 검토 대상 저장소의 라이선스 상태와 반영 방식을 기록한다.

## 원칙

1. **원문을 복사하지 않는다.** 통합한 문구는 이 저장소에서 새로 작성하고, 참고한 개념과 구성만 반영한다.
2. **라이선스가 확인되지 않은 자료는 옮기지 않는다.** 라이선스 파일이 없는 공개 저장소는 기본적으로 저작권자 권리가 유보된 상태로 본다. 같은 작성자의 저장소라도 이 저장소의 Apache-2.0이 자동으로 적용되지는 않는다.
3. **권리 범위가 섞인 자료는 제외한다.** 제3자 원문·인용·과거 기록이 섞였거나 재배포 허락이 확인되지 않은 경로는 통합하지 않는다.
4. **특정 대상이 보이는 자료는 제외한다.** 실명, 고객사, 조직, 내부 시스템, 실제 게시물 인용문이 포함된 자산은 저장소에 넣지 않는다.
5. **예시는 가상 값만 쓴다.** 실제 CVE·RHSA·계정·호스트·주소를 쓰지 않는다.

## 라이선스 판단 근거

- MIT 저장소(ChatGPT, Claude)도 이번 통합에서는 문장·코드·템플릿을 복사하지 않았다. 아이디어·구성 참고는 저작권 복제에 해당하지 않으므로 별도 고지 의무가 발생하지 않는다.
- 라이선스 파일이 없는 저장소는 원문을 전혀 옮기지 않았다. 통합 문서의 문장은 이 저장소에서 새로 쓴 것이다.
- Claude 저장소의 제3자·권리 미확정 경로(위임 루프 관련 자료, 외부 가이드 기반 기록)는 조회만 하고 어떤 파일도 복사하지 않았다. 해당 프로젝트의 고지 문서도 이 저장소로 가져오지 않았다.
- 참고한 개념의 출처는 각 저장소의 공개 이력으로 남아 있으며, 이 저장소는 원문·번역문·코드를 재배포하지 않는다.

## 제3자 고지

이번 통합으로 새로 추가된 문서에는 외부 원문의 문장·코드·템플릿 복제가 없다. 따라서 별도 저작권 표시나 라이선스 고지를 붙여야 하는 복제물은 없다. 향후 외부 원문을 직접 인용하게 되면 해당 라이선스(MIT, CC BY-SA 등)에 맞는 고지와 변경 표시가 필요하다.

## 민감정보 배제 확인

- 특정 기관·고객·개인 이름, 내부 시스템 경로·주소, 실제 게시물 인용문, 실제 CVE/RHSA 번호, 실제 계정·호스트 정보를 저장소에 넣지 않았다.
- 예시 값은 모두 가상이다. `scripts/validate_repo.py`가 실제 형식의 CVE/RHSA, 이메일, IP, 사용자 홈 경로, 토큰 패턴을 검사한다.
- 검사는 기계적 패턴 확인이며, 문장 단위의 특정 대상 포함 여부는 사람이 최종 검토한다.

## 원문 대조 검사

통합 문구가 원본 저장소 문장을 그대로 옮기지 않았는지 2026-11-01에 기계 대조했다.

- 방법: 여섯 저장소의 모든 텍스트 파일을 공백 기준으로 정규화한 뒤, 이 저장소의 신규·수정 문서에서 40자 이상 연속 일치 구간을 찾았다.
- 결과: 본문 산문 일치 0건. 남은 2건은 이 저장소가 인용한 공식 문서 URL이며 저작물 복제가 아니다.
- 코드·설정 파일의 짧은 일치는 `#!/usr/bin/env python3`, `from pathlib import Path`, JSON 스키마 URL·필드명, Markdown 표 구분선처럼 표준 상용구와 API 이름이다. 창작 표현이 아니므로 복제로 보지 않는다.
- 대조 중 20~49자 겹침 9건(문체 보정 문구와 기존 문체 규칙 일부)을 찾아 전부 새 표현으로 다시 썼다. 재검사에서 40자 이상 일치가 사라졌다.
- 한계: 연속 문자열 일치만 본다. 의미·구조의 유사성이나 번역을 통한 모방은 판정하지 않는다.

## AI-Harness (Apache-2.0) 검토

- 라이선스: Apache-2.0. 이 저장소와 호환된다. 클론 98파일을 읽고 검토했다.
- 흡수(재작성): `evidence-first` 스킬, `report-editing`·`deck-evidence`·`handoff` 레퍼런스, `scripts/blind_review.py`(개념 이식), `docs/REVIEW-CONTRACT.md`·`docs/EVALUATION.md` 보강.
- 제외: phase-gate 워크플로, 훅·서브에이전트, ToolBroker, attestation, 지식 그래프, 성숙도·배포 문서. 이 저장소는 스킬 배포용이고 런타임 하네스가 아니다(D-005·D-014 유지).
- 제3자: `design-evidence-harness` 스킬은 alchaincyf(花叔·花生) MIT, evidence-preserving 원칙은 blader/humanizer MIT를 참고한다. 이번 흡수는 개념 재작성이며 원문·코드 복사가 없다. 향후 코드를 직접 복사하면 Apache-2.0 고지와 MIT 고지를 함께 남긴다.

## 기존 유래 콘텐츠 (이번 작업 이전)

이번 작업 전에 이미 통합돼 있던 일부 문장은 같은 작성자의 이전 저장소에서 유래했다. 예: `rhel-cve`의 판정 규칙과 참조 문서, `writing`·`office-docs`의 일부 규칙.

- 소스 저장소에는 라이선스 파일이 없지만 저작자가 같으므로 재사용·재배포 권한을 확인할 수 있는 위치에 있다. 공개 배포 전에 저작자 확인을 한 번 더 남긴다.
- 이번 작업에서 새로 쓴 문장은 위 대조에서 일치가 없고, 겹친 9건은 새 표현으로 교체했다.
- 제3자 권리 주장이 생기면 해당 자산을 원복하거나 원본 요구사항만 보고 재구현한다(위 절차).

## 라이선스 문제 발생 시 대응 — 원본 참고 재구현 우선

트리거: 외부 권리 주장 접수, 배포 심사 거절, 원문과 실질 유사 발견, 라이선스 표기 누락 발견.

원칙: **원복이 아니라 원본을 참고한 다른 로직 구현이 먼저다.** 원본은 "무엇을 해야 하는가"(요구사항·동작·제약)를 확인하는 데만 쓰고, 표현·문장·코드·구조는 새로 만든다. 원복은 재구현이 불가능하거나 시간이 필요할 때의 임시 조치다.

### 1단계 — 원본에서 요구사항만 확인

1. 문제가 된 원본의 README·동작·입출력·공식 문서를 읽고 "이 기능이 만족해야 하는 조건"을 목록으로 적는다.
2. 원본의 문장·코드·주석·화면 구성은 이 단계에서 옮겨 적지 않는다. 조건만 요약한다.
3. 요구사항 목록을 `docs/DECISIONS.md`의 재구현 항목에 붙인다.

### 2단계 — 다른 로직 설계

1. 같은 목적을 다른 구조·알고리즘·데이터 흐름·문장 형식으로 표현한다(예: 서술형 → 표, 단일 파일 → 단계 분리, 반복 계산 → 사전 계산).
2. 위 대장의 "다른 로직으로 구현하는 방법"을 출발점으로 삼아 이 저장소의 구조에 맞게 바꾼다.
3. 원본과 같은 인터페이스가 필요하면 이름만 유지하고 내부 구현은 새로 설계한다.

### 3단계 — 구현과 검증

1. 구현 후 `python scripts/validate_repo.py`와 `python scripts/run_tests.py`를 통과시킨다.
