# 리뷰 요청과 피드백 수용

리뷰를 시작할 때 갖출 것과, 리뷰 의견을 받았을 때의 처리 순서를 정한다.

## 리뷰 요청 패킷

리뷰어가 저장소 전체를 추측하지 않도록 다음을 함께 준다.

| 항목 | 내용 |
|---|---|
| 목적 | 이 변경이 해결하는 문제와 요구사항 |
| 범위 | BASE SHA → HEAD SHA, 변경 파일 목록 |
| 실행한 검증 | 명령·결과(실행 수·실패·skip), 실행 환경 |
| 알려진 위험 | 의도적으로 남긴 제약, 미확인 항목, 범위 밖 변경 |
| 제외 범위 | 리뷰하지 않아도 되는 파일·영역 |
| 급함 | 머지 일정과 필수 수정 기준 |

- 리뷰어에게 대화 이력을 통째로 넘기지 않는다. 위 패킷과 diff가 기준이다.
- 검증을 실행하지 않았다면 "실행하지 않음"을 명시한다.

## 5축 리뷰

| 축 | 확인 |
|---|---|
| 정확성 | 요구 일치, 경계·오류 경로, 호출자 영향 |
| 가독성·단순성 | 이름·구조, 불필요한 추상화, 삭제 가능한 코드 |
| 아키텍처 | 기존 경계·의존 방향 유지, 순환·중복 |
| 보안 | 입력·인증·비밀값·권한 (상세는 `security.md`) |
| 성능 | 불필요 반복, N+1, 메모리, 타임아웃 |

승인 기준은 "전체 코드 건강이 확실히 나아지는가"다. 완벽하지 않다는 이유로 막지 않고, 기존 관례를 따르면 승인한다.

## 피드백 수용 순서

1. 끝까지 읽고 반응하지 않는다.
2. 요구를 자기 말로 다시 쓴다. 불명확하면 멈추고 질문한다.
3. 코드베이스·실행 결과와 대조해 타당성을 평가한다.
4. 타당하면 기술적으로 수용하고, 아니면 근거를 들어 반박한다.
5. 한 번에 하나씩 구현하고 각각 검증한다.

## 금지

- "맞습니다", "좋은 지적입니다" 같은 수행적 동의
- 검증 전에 일괄 적용
- 불명확한 항목을 추측으로 구현
- 리뷰 지적을 테스트 약화·예외 처리로 덮기

## 품질 기준 약화 신호

다음이 diff에 보이면 `차단` 또는 `중요`로 올린다.

- 테스트 skip·삭제, 단언 제거, 커버리지 제외 추가
- `@ts-ignore`, `eslint-disable`, `# noqa`, `# type: ignore`의 무근거 추가
- 미구현 stub·TODO로 테스트를 통과시키기
- 임계값·타임아웃·재시도 횟수를 근거 없이 낮추기
- 예외 삼키기, 오류 메시지 제거

## 최소 변경 확인

- 요청 범위 밖 추상화·옵션·의존성 추가가 없는가
- 기존 헬퍼·패턴을 재사용했는가
- 삭제로 해결할 수 있는 것을 추가로 해결하지 않았는가
- 변경이 닿아야 할 호출자·테스트·설정을 모두 포함했는가
