# 체계적 디버깅

장애를 만났을 때 수정 전에 원인을 좁히는 절차다. RCA 보고서 작성 전 단계에 해당한다.

## 철칙

- 근본 원인 조사를 마치기 전에는 수정안을 내지 않는다.
- 증상만 없애는 수정은 실패로 본다. 같은 원인이 다른 경로에서 다시 나타난다.
- 급할수록 추측을 줄인다. 재시도로 덮는 것은 조사가 아니다.

## 1단계 — 증상 고정

- 재현 절차, 입력, 환경, 발생 빈도, 시작 시점을 기록한다.
- 기대 동작과 실제 동작을 문장으로 나눈다.
- 로그·오류 메시지 원문을 확보한다. 요약보다 원문이 낫다.

## 2단계 — 범위 축소

- 최근 변경(배포·설정·의존성·데이터)을 시간순으로 본다.
- 입력·환경·설정을 하나씩 바꿔 최소 재현을 만든다.
- 이분 탐색으로 문제 구간을 절반씩 줄인다.
- 호출 경로를 따라가며 어느 계층에서 처음 어긋나는지 찾는다.

## 3단계 — 계측과 가설

- 가설마다 "참이면 무엇이 관측되어야 하는가"를 먼저 적는다.
- 로그·지표·트레이스를 추가하거나 재현 실험으로 예측을 확인한다.
- 반증을 먼저 시도한다. 맞는 증거만 모으면 확증 편향이 된다.
- 한 번에 변수 하나만 바꾼다.

| 가설 | 예측 | 측정 | 판정 |
|---|---|---|---|
|  |  |  | 채택·기각·보류 |

## 4단계 — 원인 확정과 수정

- 가설이 재현·증거로 확인되면 근본 원인으로 확정한다.
- 수정은 원인을 제거하는 최소 변경으로 한다.
- **회귀 테스트**: 원 증상을 재현하던 테스트를 먼저 만들고, 수정 후 통과를 확인한다.
- 같은 원인의 다른 호출자를 찾아 함께 고친다.
- 재발 방지(경보·가드·한도)를 별도로 제안한다.

## 금지

- 원인 미확인 상태에서 수정부터 시도하기
- 실패한 수정을 반복하며 변수를 여러 개 바꾸기
- 오류를 삼키거나 타임아웃을 늘려 증상 숨기기
- "환경 문제"라고 단정하고 증거를 남기지 않기
