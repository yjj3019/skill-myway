# Confluence용 RHEL CVE 리포트 형식

CVE 한 건은 `CVE-YYYY-NNNNN_리포트.md`, 여러 건이나 RHSB는 `RHEL_CVE_리포트_YYYYMMDD.md`로 저장한다. 파일 구조를 `scripts/check_report.py`로 검사하고, 사실·출처는 원문과 별도로 대조한다. 구조 검사 통과는 사실 확인이 아니다.

## 구조

제목·순서·표 컬럼을 고정한다. 단건 리포트는 단일 CVE 제목과 고정 템플릿을 쓴다. 통합 리포트는 상위 제목에 접수·고유 건수를 밝히고, `### CVE-ID`별로 단건 1~5장 블록을 반복한다. 통합 패키지 표에 `CVE ID` 첫 컬럼을 추가해 각 행을 CVE에 연결한다. `Environment`, 각 패키지 표 제목, 통합 보고서 마지막 `참고문서`는 Setext 제목이다.

```markdown
# {CVE-ID} - {원인과 결과를 담은 한국어 한 문장 설명}

보안등급

Impact : {Critical/Important/Moderate/Low 또는 미확인}
CVSS v3 Base Score : {점수 또는 미확인} (Red Hat 기준. 타 기관 점수가 다르면 병기)

기준일 : {YYYY-MM-DD} ({확인한 자료}, 공개일 {YYYY-MM-DD}{, CISA KEV 등재 YYYY-MM-DD})

Environment
-----------

* Red Hat Enterprise Linux {N} ({스트림, 필요 시})

### 1. 취약점 개요

* **분석 대상 제품**
  * RHEL 버전별 상태와 범위를 한 줄씩 (평가 데이터 없음, Out of support scope 포함). 이 줄은 요약이며 패키지 표가 고유 상태·NVR·RHSA 상세 근거다.
* Red Hat 설명 원문 1문장(따옴표)
* 원인, 공격 조건, 업스트림 영향·수정 버전, 발견자

### 2. 영향

* 악용 조건(하위 bullet), 기관별 CVSS 벡터 차이, 기본 구성·미설치 시 영향 여부

### 3. 완화 방법(Mitigation)

* Red Hat Mitigation 원문 의역 → 확인된 명령(코드 블록) → 부작용
* 완전한 해결은 패치뿐입니다.

### 4. 추가 정보

* 점검 명령(코드 블록), Bugzilla·CWE, EPSS·KEV 값과 기준일
* Red Hat 데이터 특이사항, JSON·XML 일치 여부, RHSA 확인 범위, 대체 소스, ELS 계약 안내

### 5. 결론

* 우선순위, 버전별 권고, 미패치 스트림, 악용 근거 (가능하면 4문장 이내)

영향을 받는 패키지 및 발행된 레드햇 보안 공지 ( {YYYY-MM-DD} 기준 )
------------------------------------------

{대상 CVE와 표 작성 기준 한 줄}

| RHEL | Lifecycle | Components | Fixed Package | RHSA | Release Date | 비고 |
| --- | --- | --- | --- | --- | --- | --- |

명시적으로 영향을 받지 않는다고 언급되지 않은 한, 이 목록에 있는 제품의 모든 마이너 업데이트 스트림에 포함된 기존 패키지 버전은 모두 취약한 것으로 간주해야 하며, 전체 분석이 이루어지지 않았을 수도 있습니다.

참고문서
----

* [제목](실제 조회한 URL)
```

### 다건·RHSB 통합 리포트

- 상위 제목은 `# RHEL CVE 통합 리포트 - 접수 N건 → 고유 M건` 형식으로 쓴다. 고유 1건이면 단건 파일 형식으로 전환한다. 통합 제목 자체는 CVE ID들을 나열하지 않으며, CVE별 ID는 각 `### CVE-ID` 구획과 공유 표에서 연결한다.
- `Environment` 다음에는 `### CVE-2099-NNNNN` 제목 아래 1~5장 단건 본문을 CVE별로 반복한다. 각 CVE의 보안등급·CVSS·영향·완화·결론을 서로 섞지 않는다.
- 공유 표는 `CVE ID | RHEL | Lifecycle | Components | Fixed Package | RHSA | Release Date | 비고` 8개 컬럼이다. 각 행에 CVE ID를 넣고, 모든 CVE가 한 행 이상 연결돼야 한다. 중복 제품 패키지 행은 근거가 동일할 때만 정규화한다.
- RHSB 원문에서 CVE·RHSA 목록을 확인하고 CVE별 수집·판정을 분리한다. 제목의 접수 수는 입력에서 추출한 CVE 발생 건수, 고유 수는 대문자 정규화·중복 제거 후 CVE 수다. 접속 실패·범위 축소는 각 CVE 구획이나 비고에 남긴다.
- `scripts/check_report.py`는 단건 파일명·7컬럼 리포트와 통합 파일명·건수·CVE별 1~5장·8컬럼 표/CVE 연결을 검사한다. 조사 사실·출처는 검증하지 않는다. 테스트 케이스와 실제 외부 데이터를 혼동하지 않도록 가상 CVE fixture는 별도 파일로 유지한다.

## 표 규칙

- 행 순서는 RHEL 10 → 6, 같은 메이저 안에서는 최신 스트림 먼저. `package_state`와 `affected_release`를 모두 옮긴다.
- Fixed Package: NVR + 아키텍처(`.x86_64`/`.noarch`). 비교는 원본 EVR에서 epoch를 보존하고 RPM 규칙으로 마친 뒤, 고객 양식이 요구할 때만 표시용 epoch를 생략한다. 미수정은 `미발행 ({fix_state})`, 데이터 없음은 `평가 데이터 없음`, 확인 못 한 값은 `미확인`.
- RHSA: `[RHSA-YYYY:NNNNN](https://access.redhat.com/errata/RHSA-YYYY:NNNNN)`, 없으면 `-`.
- Release Date: `YYYY-MM-DD`. 비고에 ELS 채널, errata 본문 미확인, 이상 데이터 여부를 적는다.
- 표 아래에 생성일·타임스탬프 등 메타정보를 붙이지 않는다.

## 문체

- 합니다체, 짧고 단정적인 문장. "~것으로 판단된다/보인다" 반복, 장황한 연결 설명체를 쓰지 않는다.
- 확인 못 한 것은 "확인하지 못했습니다" 또는 `미확인`. 추측으로 채우지 않는다.
- 명령·패키지명은 `code`, 강조는 `**굵게**`. HTML 태그, 이모지, 색상 배지, AI 도구명을 넣지 않는다.
- 참고문서에는 실제로 조회한 URL만 넣는다.

## 작성 및 검증

- Red Hat 영향도와 CVSS는 원문에서 확인한 값만 쓴다. `CVSS v3 Base Score` 칸에는 v3로 확인된 점수만 넣고, 기관별 점수가 다르면 출처와 차이를 병기한다. 버전 미제공 점수는 `미확인`으로 두고 4장에 별도 기재한다.
- `Environment`의 RHEL 메이저 판정은 Hydra `product_name`의 정확히 일치하는 행을 근거로 한다. EUS·E4S·ELS 등은 별도 스트림으로 표시한다. Statement만으로 영향을 판정하지 않는다.
- 단건 패키지 표는 7개 컬럼을 유지한다. `package_state`와 `affected_release`를 구분하고 패치 미발행·미확인 스트림도 누락하지 않는다. 모듈 ID만 확인된 경우 비고에 모듈 스트림 버전임을 표시한다. 다건 통합 표는 `CVE ID`가 추가된 8개 컬럼이다.
- 표 아래 고정 문구는 제공된 형식의 일반 주의문이며 각 제품·스트림이 실제로 취약하다는 독립 근거가 아니다. 확인된 제품별 상태와 분석 범위를 본문과 표에 명확히 구분한다.
- 이상 데이터 판정(judgment-rules.md 8절)에 해당하면 4장 "Red Hat 데이터 특이사항"과 표 비고에 기록한다.
- 완화 조치의 확인·적용·검증·원복 명령과 부작용은 실제로 확인한 내용만 적는다. 확인하지 못한 명령은 만들지 않는다. 완전한 해결은 패치뿐이라는 문구는 보안 공지가 명시한 경우에만 쓴다.
- 악용 사실은 출처를 명시하며 Red Hat 공지에 없는 정보는 구분한다(judgment-rules.md 9절). EPSS·KEV를 사용하면 확인 시점과 근거를 4장 또는 5장에 적는다. 로그인 장벽이나 자료 접근 실패, 범위 축소, 대체 소스는 4장에 기록한다.
- 참고문서는 실제로 조회한 URL만 포함한다. 점수·NVR·RHSA·발행일을 원문과 수동 대조한다. 한국어 합니다체를 사용하고 HTML·색상 배지·이모지를 넣지 않는다.
- 전달 메시지는 산출물 경로, 핵심 판정(KEV·버전별 조치) 3~5줄, 미확인·판단 필요 항목, 출처 목록으로 짧게 쓴다. 외부 시스템(Confluence 등) 게시는 사용자가 요청할 때만 한다. 고객명·호스트명·담당자명은 리포트에 넣지 않는다.
